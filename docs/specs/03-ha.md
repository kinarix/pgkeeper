# 03 — High Availability: Replication, Lease, Fencing, Switchover, Failover, Pinning, Rolling Updates

This is the most safety-critical spec. Changes to anything in §3–§7 require: an updated invariant table (§1), new/updated model tests (08 §3.2) and a passing ledger chaos run (08 §3.6). Design rationale for the lease: ADR-016.

## 1. Invariants (must hold at all times)

| ID | Invariant | Enforced by |
|---|---|---|
| I1 | At most one instance runs Postgres **not in recovery** and accepts connections, *as observed by any client at any instant*, except for the bounded window in I1a and the process-freeze case in §3.6 (closed for acknowledged writes only by `dataDurability: Required`). | Lease protocol §3 |
| I1a | A primary that no longer holds valid grants forming a sustain quorum (§3) stops accepting writes within `renewDeadline + fenceTimeout` of the send time of its last renewal that completed such a quorum, and that sum is `< lease.duration`. | IM holder rule §3.3, CEL rule on `ha.lease` |
| I2 | An instance is promoted only if it holds grants forming an acquire quorum (§3) **and** the operator's `status.targetPrimary` names it. | IM promote path |
| I3 | With `synchronous.dataDurability: Required`, the operator never promotes an instance that is not guaranteed to have every commit acknowledged under `synchronous_commit = on` or `remote_apply` (§6). Commits made with `local` or `off` (a session/role/database override) are not covered; `remote_write` is covered unless the standby's node also loses power. | Candidate selection §5.3 |
| I4 | A demoted/failed primary never rejoins as a replica without first checking timeline divergence and running `pg_rewind` (or re-cloning). | IM rejoin §5.5 |
| I5 | The operator never deletes a PVC of the current primary, nor the last PVC holding the most advanced LSN. | Operator scale-down/replace logic |
| I6 | Two clusters never archive WAL to the same store path. | CEL + reconcile check (04 §2) |
| I7 | A voter never holds unexpired grants for two different candidates; its term and `voterEpoch` never decrease, including across restarts. Every acquire quorum intersects every sustain quorum, under both voter sets during a membership change. | Voter rules §3.2, membership §3.5, model tests |

## 2. Streaming replication

- Replication user `streaming_replica`, `REPLICATION` attribute, authenticated **only** by client certificate (`hostssl replication streaming_replica <pod CIDR> cert`). Certs in `<cluster>-replication-tls`, rotated by operator.
- Each replica connects to `<cluster>-rw` (Service follows the primary), not to a pod IP: no reconfiguration needed after failover besides restart into recovery.
  `primary_conninfo = 'host=<cluster>-rw port=5432 user=streaming_replica sslmode=verify-full sslcert=... sslkey=... sslrootcert=... application_name=<instance> keepalives_idle=5 keepalives_interval=2 keepalives_count=3 tcp_user_timeout=10000'`
- **Slots:** primary IM maintains one physical slot per replica, named `pgkeeper_<instance with - → _>`; operator passes the desired list via `/v1/slots/reconcile`. Slots for removed instances are dropped. `max_slot_wal_keep_size` (from spec) caps disk blow-up from a dead replica — a replica that falls past it must be re-cloned (IM detects `requested WAL segment ... has already been removed` and reports `NeedsReclone`; operator deletes and recreates that instance's PVC — never the primary's).
- After failover the new primary must create slots for remaining replicas **before** they reconnect; operator does this as part of the promotion workflow. (PG17's `sync_replication_slots` concerns logical slots — out of scope.)
- `wal_log_hints = on` always (needed by pg_rewind even with checksums off).
- `hot_standby = on`; `hot_standby_feedback` user-configurable (default off).
- Status: per replica `received`, `replayed` LSN, `lagBytes` (primary current LSN − replica flush LSN from `pg_stat_replication`), `syncState`.

## 3. The primary lease protocol (quorum lease, ADR-016)

The lease is granted by **voters**: the `coordination.k8s.io/v1 Lease` named `<cluster>-primary` (the *Lease voter*) plus, in `spec.ha.quorum.mode: Peers`, every instance manager in the current voter set (*instance voters*, n of them). Leadership has a **term** that only increases, like a Raft term or a Kafka leader epoch.

| Action | Needs valid grants from |
|---|---|
| **Sustain** (keep accepting writes) | the Lease voter **or** ≥ `Qs` instance voters |
| **Acquire** (promote) | the Lease voter **and** ≥ `Qa` instance voters |

`Qs = ⌊n/2⌋ + 1`, `Qa = n − Qs + 1`, so `Qa + Qs > n` and every acquire quorum intersects every sustain quorum. The holder's own vote counts. With n = 1, or in mode `KubernetesLease`, the instance path is disabled and the Lease voter alone decides (sustain = acquire = Lease).

| n | Qs / Qa | Primary keeps writing when… | Failover possible when… |
|---|---|---|---|
| 1 | Lease only | API server reachable | — |
| 2 | 2 / 1 | API reachable (replica may be dead), **or** replica reachable | API reachable + the candidate |
| 3 | 2 / 2 | API reachable (both replicas may be dead), **or** ≥ 1 replica reachable | API reachable + candidate + 1 |
| 5 | 3 / 3 | API reachable, **or** ≥ 2 replicas reachable | API reachable + candidate + 2 |

Time handling follows client-go leader-election semantics: expiry is measured on each party's own **monotonic** clock, never by comparing wall clocks. Requirement: bounded clock *rate* drift between nodes, not clock sync.

### 3.1 Lease voter
Fields used: `holderIdentity` (instance name), `leaseDurationSeconds`, `acquireTime`, `renewTime`, `leaseTransitions`, annotations `pgkeeper.in/term` and `pgkeeper.in/voter-epoch`. Updates are optimistic (resourceVersion). A non-holder treats the Lease as expired when `monotonicNow() - lastObservedChange > leaseDurationSeconds`, or when it was released (`holderIdentity == ""`).

### 3.2 Instance voters (mode `Peers`)
Voter V grants candidate C for term t (`POST /v1/vote`, mTLS, 02 §7) only if:
1. t ≥ V's stored term;
2. V holds no unexpired grant to a different candidate;
3. C == `status.targetPrimary` as last seen by V (informer cache; kept at its last value while the API server is unreachable);
4. the request carries V's current `voterEpoch` (§3.5).

The grant expires at V's monotonic now + `leaseDuration`; renewals by the current holder extend it under the same rules. V persists (candidate, term, voterEpoch) in `$PGDATA/pgkeeper/vote` with fsync before answering. After a restart V treats its persisted grant as freshly given and refuses other candidates for a full `leaseDuration`.

### 3.3 Holder (primary IM) loop
```
every retryPeriod (renew loop):
  for each voter in parallel:
      sent := monotonicNow()
      if renew(voter) ok: validUntil[voter] = sent + renewDeadline
  healthyLocal := !crashLoop && !startTimedOut && !(crashPolicy == FailoverImmediately && postmasterCrashed)
                                                   # a postmaster restarting within spec.ha.crashHandling counts as healthy (§3.7)
  wanted := clusterCR.status.targetPrimary == me   (cache; if stale > renewDeadline keep last value)
  if !healthyLocal or !wanted:
      fence(); release(); goto ReplicaPath           # voluntary step-down

independent deadline timer (fires at the earliest time the valid grants stop forming a sustain quorum):
  if !sustainQuorum(validUntil, monotonicNow()):
      fence()                                        # involuntary: cannot prove we still hold it
```
`fence()` = `pg_ctl stop -m immediate`, then SIGKILL process group after `fenceTimeout`. **Immediate** stop terminates every client backend at once, so pooled connections error out and reconnect via `-rw` — the failure mode where clients keep writing to an isolated primary for minutes is closed by construction. The deadline timer is separate from the renew loop so a slow or hanging renew call can never delay fencing.

### 3.4 Acquirer (promotion candidate) rule
An instance may promote only if it is named by `status.targetPrimary` **and** it holds valid grants forming an acquire quorum for a term higher than any it has seen. The Lease voter grants only when the Lease is free or expired (§3.1); instance voters grant per §3.2.

Safety: every way the old holder could sustain shares a voter with the new acquire quorum. That voter granted the new candidate only after its grant to the old holder expired, `leaseDuration` after the old holder last renewed there. The old holder stops counting that grant at `sent + renewDeadline` and fences within `fenceTimeout`, so it is down first (I1a). Safety margin = `leaseDuration − renewDeadline − fenceTimeout` (defaults 15 − 10 − 3 = 2 s); CEL rejects a non-positive margin.

### 3.5 Voter-set membership (mode `Peers`)
- The operator publishes the instance voter set and a monotonically increasing `voterEpoch` in `<cluster>-config`.
- Changes: scale up/down (§10), replacement of a stranded instance (§11), re-adding a recovered instance, and **removal of an instance failed for `spec.ha.quorum.voterRemovalDelay`** (default 30 s; CEL: ≥ 2 × `lease.duration`). Removal shrinks n and `Qa`, so sequential failures can still fail over down to the last survivor.
- **Joint quorums:** until a change completes, sustain and acquire must hold under **both** the old and the new set. A change completes when the current holder has renewed under the new `voterEpoch` with a sustain quorum of both sets, or, with no holder, when an acquire quorum of the old set has acknowledged the new epoch.
- **Forced removal** (no acknowledgement) only via a human-confirmed PostgresSwitchover with `pgkeeper.in/force-promote` (§5.3 step 5), for simultaneous failures where the survivors cannot form an acquire quorum.
- Exact commit rules are fixed in the Phase 10b model test before implementation.

### 3.6 What the lease cannot protect against (documented, tested)
- **Process freeze** (VM pause, long GC/stop-the-world on the node, SIGSTOP): a frozen primary resumes and may serve a few writes before its IM loop notices. Patroni mitigates with a hardware/soft watchdog, unavailable in unprivileged pods. Mitigation here: `synchronous.dataDurability: Required` — writes on a stale primary block because its standbys now follow the new primary and won't acknowledge. **[High Confidence]** this is the only complete fix.
- **Async replication loss:** writes acknowledged by the old primary and not yet streamed are lost on failover. Bounded by `maxFailoverLag` for candidate eligibility, not eliminated.

### 3.7 Postmaster crashes while holding the lease (ADR-019)
- Default `spec.ha.crashHandling.policy: RestartInPlace`: the holder keeps renewing and restarts Postgres with backoff. No writes are possible while Postgres is down, so holding the lease is safe; the deadline timer stays armed during crash recovery, and Postgres is (re)started as primary only while a sustain quorum is valid.
- Escalation: `maxRestarts` crashes within `window`, or no accepted connection within `startTimeout` after a restart → stop, `CrashLoop`, release with `release-reason=CrashLoop` or `RecoveryTimeout` → failover (§5.1) without expiry wait.
- `FailoverImmediately`: first crash → release with `release-reason=Crash`.
- If failover isn't possible (n = 1, `Strict` pin on this instance, `QuorumUnavailable`, `NoEligibleCandidate` — published by the operator as `failoverPossible: false` in `<cluster>-config`; last value kept while the API server is unreachable), the IM keeps restarting at `backoff.max` and keeps the lease; condition `CrashLoop`.
- Counts as a crash: unrequested postmaster exit, or Postgres reinitialising after a backend crash. Never: fence, switchover, SIGTERM, operator-requested restart.

## 4. Fencing (manual)
- Annotation `pgkeeper.in/fence: "<instance>|<instance>"` on the cluster. IM of a fenced instance stops Postgres (immediate if primary), stays `role: fenced`, keeps PGDATA. Used for forensics/maintenance.
- Fencing the primary triggers normal failover (unless `pin.policy: Strict`).
- Removing the annotation lets the instance rejoin through §5.5.

## 5. Automatic failover

### 5.1 Failure detection (operator)
Primary considered failed when **any** of:
- the holder **cannot be sustaining**: the Lease voter hasn't changed for `lease.duration` (operator's observation clock) **and**, in mode `Peers`, at least `Qa` instance voters positively report via `/v1/status` that their grant to the holder expired (together an acquire quorum, which intersects every sustain quorum). In mode `KubernetesLease` the first condition alone suffices;
- Lease released by holder with reason annotation (`pgkeeper.in/release-reason`: `Unhealthy|Crash|CrashLoop|RecoveryTimeout|Shutdown`; §3.7). A `Shutdown` release carrying `pgkeeper.in/shutdown-lsn` is handled as a handoff (§7.1), not a plain failover;
- Primary pod deleted / node gone (pod `DeletionTimestamp` or node `NotReady` > `lease.duration`) **and** the first condition holds.

IM `/v1/status` reachability alone never triggers failover (the operator may be the partitioned party): an unreachable voter counts as "no report", never as "expired". A primary cut off from the API server but still sustained by its peers is therefore neither fenced nor failed over.

### 5.2 Flap damping
- `failoverDelay` (default 0): wait this long after detection before electing.
- Back-to-back failovers: if the last failover was < 5 min ago, require `2 × failoverDelay` (minimum 30 s) — prevents ping-pong under flaky networks. Recorded as event `FailoverDamped`.

### 5.3 Candidate selection (pure function, unit/property tested)
Input: replica statuses reachable within 5 s, cluster spec, last known primary LSN.
1. Exclude: fenced, not streaming/receiving in last `lease.duration`, `NeedsReclone`, `CrashLoop`, pod terminating, on the same node as failed primary if node is NotReady (stale view risk).
2. If `pin.policy == Strict`: candidates = {pinned} only — if absent, **no failover**; set condition `PrimaryAvailable=False reason=StrictPinWaiting`.
3. If `pin.policy == Preferred` and pinned is a valid candidate within `maxFailoverLag` of the best: pick pinned.
4. If `synchronous.dataDurability == Required` (mode Quorum ANY k of n-1): pick the replica with highest **flush** LSN among all reachable replicas, and only proceed if at least `n-1 - k + 1` replicas reported (otherwise the acknowledged-write holder might be unreachable → wait, condition `QuorumUnavailable`).
5. If the reachable, non-excluded instances cannot form an acquire quorum (simultaneous loss of the primary and other voters before removal, §3.5): no failover; condition `QuorumUnavailable`. A human may force it with a PostgresSwitchover `mode: Fast` + annotation `pgkeeper.in/force-promote: <instance>` after confirming the lost instances are really down; the operator then removes them from the voter set without acknowledgement.
6. Else pick max flush LSN; exclude any candidate whose lag vs last known primary LSN > `maxFailoverLag` (if all excluded → wait, condition `NoEligibleCandidate`; user can force with a PostgresSwitchover `mode: Fast` + annotation `pgkeeper.in/force-promote: <instance>`).
7. Tie-break: lowest replay lag, then lowest serial.

### 5.4 Promotion workflow
1. Operator sets `status.targetPrimary = C`, `phase = FailingOver`, emits event.
2. All IMs observe; old primary (if alive) steps down voluntarily via §3.3.
3. C's IM: obtains an acquire quorum per §3.4 (new term), waits for WAL replay to finish received WAL (`pg_last_wal_receive_lsn() == pg_last_wal_replay_lsn()` or 10 s), calls `pg_promote(wait => true)`.
4. Operator observes C `role=primary` via status API → relabels pods (`pgkeeper.in/role`) — **remove** `role=primary` from the old primary's pod first, then add it to C, so `-rw` never selects two pods — reconciles slots on C, updates `currentPrimary`, `timeline`, `lastFailover`, and creates/updates the cluster's `PostgresPrimaryOverride` to C (§8.1); condition `FailoverUnacknowledged=True`.
5. Other replicas' IMs restart their WAL receiver (new timeline via `recovery_target_timeline=latest`).
Target write-unavailability for unplanned failover with defaults: ≤ 30 s (lease 15 s + detection ≤ 2 s + replay + promote + EndpointSlice propagation). Measured and reported by ledger tests. No failover is possible while the API server is unreachable (the operator can't set `targetPrimary` and `-rw` can't be re-routed); existing primaries keep running per §3.

### 5.5 Rejoin of a former primary
On start (or after fence clears), IM with existing PGDATA and lease held by someone else:
1. Read local timeline & last checkpoint LSN (`pg_controldata`).
2. Fetch new primary's timeline history (replication protocol `TIMELINE_HISTORY` via `pg_rewind --dry-run` or IM's own query).
3. If local history diverged after the fork point: `pg_rewind --target-pgdata=$PGDATA --source-server='host=<cluster>-rw dbname=postgres user=pgkeeper_rewind sslmode=verify-full sslcert=… sslkey=… sslrootcert=…' --progress` (no `-R`; IM writes config). pg_rewind uses a **normal** connection, not a replication one, so it authenticates as the dedicated role `pgkeeper_rewind` (cert auth; `EXECUTE` on `pg_ls_dir(text, boolean, boolean)`, `pg_stat_file(text, boolean)`, `pg_read_binary_file(text)`, `pg_read_binary_file(text, bigint, bigint, boolean)`; HBA in 05 §4). If the target wasn't shut down cleanly (crash, fence), pg_rewind runs single-user crash recovery first (PG13+ default).
4. If rewind fails (missing WAL, etc.): report `NeedsReclone`; operator replaces PVC (I5 respected).
5. Start in recovery; stream.

## 6. Synchronous replication
- `mode: Off` → `synchronous_standby_names = ''`.
- `mode: Quorum, number: k` → `synchronous_standby_names = 'ANY k (inst-a, inst-b, ...)'` listing current replicas' `application_name`s; maintained by the primary IM on topology change.
- `dataDurability: Preferred` → if fewer than k replicas are healthy, IM shrinks the list (or empties it) so writes keep flowing; condition `SynchronousDegraded`. Availability over durability.
- `dataDurability: Required` → list never shrinks; writes block when < k standbys ack. Durability over availability. Interacts with §5.3 step 4. The server default `synchronous_commit` is `on`; `synchronous_commit` remains overridable per role/database/session (02 §4.2), and such overrides are outside I3. The IM reports role/database overrides found in `pg_db_role_setting` as condition `SynchronousCommitOverridden` (warning) so they are visible.
- Single-instance clusters reject `mode: Quorum` (CEL: `number < instances`).

## 7. Planned switchover (`PostgresSwitchover`)
Goal: a few seconds of write unavailability, zero lost commits, no pg_rewind. Both modes keep this guarantee; `Fast` only skips the preparation.
1. **Validate:** cluster Healthy; no active switchover/failover; target (given or best per §5.3) streaming with lag < 16 MiB; pin compatibility.
2. **Drain (`Graceful` only):** operator sets pooler PAUSE if a pooler with `pauseOnSwitchover` exists (Phase 27). Primary IM: `CHECKPOINT` (shrinks shutdown time).
3. **Demote:** operator sets `status.targetPrimary = target`. Old primary IM: `pg_ctl stop -m fast` — both modes; a fast shutdown writes a shutdown checkpoint and its WAL senders stream all remaining WAL before exiting, so the shutdown checkpoint LSN in `pg_controldata` is the true end of WAL. Wait up to `timeout/2` (`Graceful`) or `min(10 s, timeout/2)` (`Fast`). Then **release** the lease with `release-reason=Switchover` and `pgkeeper.in/shutdown-lsn=<lsn>`.
   - If the fast stop doesn't finish in time, the IM escalates to `-m immediate`. After an immediate stop the checkpoint LSN is **not** end of WAL, so the release carries no `shutdown-lsn`; the switchover completes as a failover to the target (status `lossy: true`, event `SwitchoverDegraded`) and the old primary rejoins via the rewind check (§5.5).
4. **Promote:** target IM waits until its received/replayed LSN ≥ shutdown LSN (guarantees no lost commit; timeout → abort, old primary restarts and re-acquires — operator resets targetPrimary), obtains an acquire quorum immediately (no expiry wait: the old holder released the Lease voter and its instance grants), promotes.
5. **Rejoin:** old primary starts as replica of new; no divergence because it shut down cleanly after the target received everything — `pg_rewind` check still runs (I4) and should be a no-op (except after the immediate escalation in step 3).
6. **Resume** pooler; record `writeUnavailableMillis` (from old primary stop to new primary first accepted write, measured by operator probe connection).
7. **Record:** for a human-requested switchover, create/update the cluster's `PostgresPrimaryOverride` to the target (§8.1), so a pin never silently pulls the primary back. Operator-initiated switchovers (rolling update, eviction §9) only update an *existing* override; switchbacks to the pin create nothing.

### 7.1 Shutdown handoff (SIGTERM on the primary, ADR-021)
When the primary pod gets SIGTERM outside a switchover (pod delete, eviction that wasn't pre-empted by §9 step 5, node shutdown), the IM performs step 3 above on its own: fast stop (≤ `terminationGracePeriodSeconds − 5 s`, then immediate), shutdown LSN, release with `release-reason=Shutdown` + `pgkeeper.in/shutdown-lsn`.
- The operator picks the best candidate (§5.3) whose received LSN reaches the shutdown LSN within `min(10 s, lease.duration)`, sets it as `targetPrimary`, and it promotes without an expiry wait — **zero lost commits**, no rewind.
- No candidate reaches the LSN in time, or no `shutdown-lsn` (immediate fallback) → normal failover (§5.3–§5.4).
- Treated as an operator-initiated switchover for the override (§8.1): updates an existing override, never creates one. With a `Preferred` pin on the restarted pod, the primary moves back once that pod is healthy again.
- Single-instance clusters: no handoff; the pod restarts with the same PVC.

## 8. Primary pinning (`spec.primary.pin`)
| Policy | Behaviour |
|---|---|
| unset | normal |
| `Preferred` | With **no override present**: when the pinned instance is healthy and caught up (lag < 16 MiB) and is not primary, operator performs an automatic Graceful switchover to it (e.g. right after the pin is first set). If the pinned instance fails, normal failover proceeds and creates an override (§8.1); the pinned instance becomes primary again only after a human deletes the override. |
| `Strict` | Only the pinned instance may ever be primary. If it fails, the cluster stays without a primary (read-only replicas) until it returns or the pin is removed. Requires `acknowledgeStrictRisk: true`. Condition `StrictPinWaiting`. |

Interactions: switchover to a non-pinned target is `Rejected` under Strict; allowed under Preferred (it updates the override, §8.1, so the pin does not pull back). Removing a pin never triggers a switchover. Pinning to a non-existent instance sets `PinTargetInvalid` and is otherwise ignored.

### 8.1 Primary override (ADR-017)
- `status.targetPrimary` is computed by one pure function (`internal/ha`) with fixed precedence: **`PostgresPrimaryOverride` > `spec.primary.pin` > candidate selection (§5.3)**. Failover and switchover are the only ways the override's instance changes; both are decided by the operator first and then recorded in the override.
- The operator creates/updates `<cluster>-primary-override` after every automatic failover (§5.4 step 4) and every completed human-requested switchover (§7 step 7); operator-initiated switchovers only update an existing one. It **never deletes** it. A human deletes it to acknowledge (dashboard: "Acknowledge failover").
- While it exists: `FailoverUnacknowledged=True`; alert `FailoverUnacknowledged` (info) after 24 h.
- If the override's instance fails, normal failover (§5) runs and the override is updated to the new primary (history appended).
- On deletion: `Preferred` pin naming a non-primary instance → Graceful switchover to it when healthy and lag < 16 MiB (`Progressing reason=SwitchbackWaiting` until then); otherwise nothing moves.
- `Strict` pins never fail over, so never create an override.

## 9. Rolling updates (primary-aware)
Triggers: image digest change (same major), tools image change (operator upgrade), resources, scheduling fields, extension list, pending-restart parameters, cert-mount changes.
1. Compute per-instance desired pod spec hash (annotation `pgkeeper.in/spec-hash`).
2. Update replicas one at a time (highest serial first): delete pod → recreate with same PVC → wait Ready + streaming + lag < `maxFailoverLag`. `maxUnavailable` replicas = 1 (fixed in v1).
3. Primary last:
   - `updateMode: Supervised` → stop; condition `Progressing reason=WaitingForSwitchover`; user creates a `PostgresSwitchover` (dashboard button).
   - `updateStrategy: Switchover` → operator-initiated Graceful switchover to most up-to-date updated replica, then recreate old primary pod.
   - `updateStrategy: Restart` → restart primary in place (write outage = restart time, no topology change). Required for 1-instance clusters.
4. Parameter changes not requiring restart are applied via reload on all instances immediately (no rollout).
5. PDBs: `<cluster>-primary` (minAvailable 1 when instances>1, selector `pgkeeper.in/role=primary`) and `<cluster>-replicas` (maxUnavailable 1). **Drain of the primary's node:** `kubectl drain` cordons first, and the primary PDB refuses the primary's eviction, so no `DisruptionTarget` ever appears on the pod. The operator therefore watches the primary's **node**: when it becomes unschedulable or gets a `NoExecute` taint, the operator runs an operator-initiated Graceful switchover to a replica on a schedulable node. After the relabel the old pod is no longer selected by the primary PDB, so the drain's eviction retries succeed against the replicas PDB. SIGTERM without a prior switchover falls back to the shutdown handoff (§7.1).

## 10. Scaling
- Every scale or replace in mode `Peers` is a voter-set change and goes through joint quorums (§3.5).
- Scale up: new serial, PVC, pod clones from primary (or from backup when `spec.replication.cloneFrom: Backup` — later phase).
- Scale down: remove the replica with the **highest serial that is not pinned** and not the best failover candidate; complete its voter removal (§3.5) before deleting the pod; drop its slot; PVC per `deletionPolicy`.
- `instances: 1` → `0` not allowed (use `pgkeeper.in/hibernate: on` annotation, later phase).

## 11. Node loss with node-local storage (kind/k3d local-path, many bare-metal setups)
Local PVs pin a pod to its node. If the node is gone > `nodeLossTimeout` (default 10 min, spec field later), the instance can't be rescheduled. Operator: if instance is a replica, delete PVC+pod and recreate on another node (re-clone); if it was the primary, failover has already happened, then same as replica. Never auto-delete when it is the only instance (I5) — raise `InstanceStranded` instead. e2e must cover this because kind/k3d default storage is local-path.

## 12. Client guidance (ship in docs, referenced by dashboard)
- Connect to `<cluster>-rw`; set pool `maxLifetime` (≤ 30 min) and enable retries on `57P01 admin_shutdown`, `57P02`, connection-refused, `25006 read_only_sql_transaction`.
- libpq multi-host alternative: `host=<cluster>-rw,<cluster>-r target_session_attrs=read-write`.
- TCP keepalives on clients (`keepalives_idle` ≤ 10 s) so dead connections are detected after network partitions.
- Expect: switchover ≈ 1–5 s of errors/queueing; unplanned failover ≈ 15–30 s; async RPO = replication lag at the moment of failure.
